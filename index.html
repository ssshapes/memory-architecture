Memory architecture

The personal OS is a memory prosthesis for a frontier model. The model arrives brilliant and amnesiac: trained on everything in general, knowing nothing about this life in particular — and the particulars change daily. Every organ below exists to close that gap without ever guessing a fact, losing a day silently, or believing something it can't source. What follows is one running instance of a portable pattern — the specifics are examples; the architecture is the point.

The circulation — one prompt, end to end

The problem, precisely

A language model stores distributions, not records. It learns "what lighting manufacturers are like" from a million exposures; it cannot reliably learn "what happened Tuesday" from one. So everything specific — the people, the projects, the deadlines, the decisions — must be retrieved into the context window at the moment of use, not hoped for from the weights.

That reframes the whole system: the context window is the model's working memory, and in-context learning is functionally a temporary weight update — scoped to one session, fully auditable, instantly reversible. The OS's entire job is deciding what earns a place in that window, when, and with what proof. Retrieval quality is intelligence here; the repo is a context management system before it is anything else.

The memory taxonomy it serves

Weights
The gist
General knowledge, language, judgment priors. Learned slowly by the lab, amortized across everyone. Nothing personal lives here — it can't be audited or deleted.
Context window
Working memory
Ephemeral, precious, degrades as it fills. Holds the live thread plus whatever the organs inject. Cleared at seams between threads, never mid-thought.
Files + index
Long-term explicit
The corpus: memories, people, projects, doctrine. Every belief is a line with provenance that can be found, corrected, or deleted — the property weights can never offer.
Ledger data
Never-guess facts
VINs, balances, deadlines, entry numbers. Read deterministically from files and systems of record, never generated. A guess here is a failure, not an approximation.

The human analogy is exact, and it runs the same architecture: cortex (weights, slow), working memory (context), hippocampus (episodic capture), consolidation during sleep (/consolidate), and written records for what the brain should never improvise. Biology retrains nightly and still needs the hippocampus — which is why "just fine-tune the model on my life every night" doesn't dissolve this system. Weights can't take one-shot facts, and worse, they can't forget on command.

Inside the stores

The left column of the diagram, opened up. Four stores, four different lifecycles — but every shelf in them earned its place by answering the same three questions: what context does it hold, what triggers its retrieval, and who tends it.

Semantic memory · atomic facts ↑ diagram

One durable fact per file, 176 of them, in four types: user_ (who the principal is — role, constraints, preferences), feedback_ (how the model should work with them, always with the why), project_ (ongoing threads), reference_ (where things live and how they run). Each file carries provenance in its frontmatter — the session it came from — and links sideways with wikilinks. MEMORY.md is the index over them: one pointer line per memory, loaded into every session as the hot working set, byte-capped and gated at write time so it can't silently outgrow what a session actually reads. Cooled memories move to an archive tier: out of the always-loaded index, still fully searchable.

Episodic memory · what happened ↑ diagram

One card per conversation, written automatically when a session ends or compacts. The card holds a summary and a list of who and what was mentioned; the full transcript sits alongside it for verification. This is the raw material consolidation distills into semantic memories — and it's gated at write time so routine automation runs (in this instance, a Sunday brief and a daily news scrape) don't fill the store with cron noise. The store remembers days, not machinery.

The corpus · the repo itself ↑ diagram

Everything that isn't a memory file is the corpus: the repository's domain folders, which are the primary record, not documentation of it. The memory stores mostly point into the corpus; the corpus is where the actual state lives.

people/ — the Rolodex
One file per contact plus a network map with cadences and last touches. Triggered whenever a name appears in conversation. Serves the whole OS — school, household, venture threads — not one domain.
Domain folders — the projects
One folder per domain of the life in question — in this instance properties/ (three of them, personal vs LLC walled off), family/, yale-emba/, ai-development/. Each carries its own CLAUDE.md doc index; the root routing layer sends a topic to its domain instead of loading everything everywhere.
knowledge/ — the wiki
Two layers: raw/ keeps sources as they arrived (PDFs, clipped posts, transcripts); wiki/ keeps what they were distilled into — frameworks, source notes, recurring themes. Reading flows in by pull, gets a worth-verdict, and only the durable part is kept.
tools/ + routines/ — the machinery
The running surfaces and their specs: this board and its pages, the inbox safari, and the source-of-truth definitions for every scheduled routine the clock below executes.
index.db · the search layer ↑ diagram

Not a store of beliefs — a derived lookup over all three stores above. Rebuilt from scratch at every session start, so it can never drift far from the files; queried by the recall hook on every single prompt with hybrid search (FTS5 keyword + vector similarity, rank-fused), then expanded one hop along wikilinks so a hit drags in its neighbors. The files are the truth; index.db is how a two-second lookup finds them.

The life of a session

Everything above is plumbing for one repeating unit of work: a session. Each one is born knowing the doctrine, works with a private context window, and dies leaving everything durable on disk. The discipline is entirely at the two ends — birth is automatic, close-out is a ritual, and skipping the ritual is the only way to lose a day.

The sharing rules, precisely. When does one session see another's activity? There are exactly three answers. File writes: immediately. The moment a session saves a contact file, a status row, or a memory, every other session can read it — coordination happens by writing early and often, not by talking. Conversation content: at close-out. What was said in a window — decisions, reasoning, dead ends — exists nowhere else until the close-out ritual captures it as an episodic card and pushes conclusions into their files. Until then, other sessions can't see it at all. Unwritten context: never. A window cleared without capture takes its contents with it permanently.

Two consequences run the fleet. First, one thread per channel: since live context is private, splitting one thread across two sessions guarantees neither has the whole picture. Second, /spinoff exists because handing work to a new session means staging its context to disk first — the child cannot see the parent's conversation, so the parent writes a brief (sources, deliverables, constraints, death step) into the repo and the child's first act is to read it. Context transfer is a file, not a memory.

Other timers come and go with the work — a news scrape, a digest, a weekly evaluation batch — and every one has the same shape: a timer, a headless claude -p wrapper, and a confirmation token verified in the output, because exit codes lie. Everything runs on one always-on machine. Cloud scheduling was tried and retired: local means direct file access, one scheduler, one place to look when something misfires.

Why this and not fine-tuning

The obvious question: if the model needs to know this life, why not train it on this life? Three reasons, each sufficient. Weights can't take one-shot facts — a single day's events are statistically invisible to training, and repeating them enough to stick damages what the model already knows. Weights can't forget — a false belief smeared across parameters has no line number; in this system, a wrong memory was once caught, traced, and deleted as one file, which is the whole safety model. And the frontier isn't yours to train — a personal fine-tune rides a lesser model, trading general intelligence for familiarity; retrieval gets both.

The bet underneath: whatever the mechanism becomes — better retrieval now, some form of continual learning later — the curated, provenance-tracked corpus is the durable asset. It's simultaneously the retrieval substrate of today and the training set of whenever. The organs keep it clean; the corpus compounds.

Lineage — none of this is invented here

The system borrows on principle: for every piece, a mature discipline had already solved the problem and named the pattern — and named patterns come with vocabulary the model already understands for free. Some of it is canonical science, some of it is a gist from three months ago; both get credited. What's original is only the assembly.

Appendix — principles of the index

"Some things come forth immediately; others must be sought longer, as though dug out of more secret receptacles; others rush out in troops, and while a different thing is asked, they leap into the midst, as if to say, is it perchance I? These I drive away from the face of my remembrance, until what I wish for be unveiled and appear out of its secret place."
— Augustine, Confessions X — hybrid retrieval, ranked candidates, and a reranker, ca. 400 AD

The index is a list of lights, not a book. MEMORY.md exists so that a fresh session recognizes — the light goes on: "I know this, go look." Title plus a few words of hook is the minimum recognition unit; a bare name doesn't disambiguate, a paragraph is content smuggled into a cache. Detail always lives in the file the pointer names.

The reader determines the format. The index is read by a language model in context; the stores are read by search engines. Each gets the redundancy its reader needs. Aliases, codenames, and alternate spellings go in file bodies (uncapped, where FTS5's literal matching needs the exact string); the index never spends capped bytes on fuzziness its reader supplies for free.

The model's prior is the codebook. Compressing hooks into private notation is a false economy three ways: it discards the pretrained prior that decompresses prose for free; it requires shipping decode instructions (bytes plus error risk — a misread index is worse than a fat one); and it often loses on the true cost unit, since tokenizers are trained on prose (~4 chars/token) and symbol-soup fragments into 1–2. The most efficient encoding for a model is well-chosen natural language.

Structure by type where machines compute; prose where the model reads. Type-grouping is real compression, implemented one level up: people, companies, and properties live in their own stores with their own indexes; memory filenames carry their type prefix inside the pointer, so the tag rides for free. The general rule: format is cost when read into context, capability when computed over.

The compression frontier is selection, not encoding. Past lean hooks, bytes are recovered by consolidation (merge related entries) and eviction (a cold entry's recognition value decays toward zero while its byte cost stays constant). Evicted things stop lighting up automatically but stay fully findable — the file and the search index still hold them. Same deal biological working memory makes.

Enforced, not remembered. The pointer discipline is a write-time gate in the validator (lines over budget or files near the read ceiling are blocked with fix-it feedback), because an index that silently outgrows its read limit fails invisibly — the bottom of the file simply stops existing to every future session. Deterministic rules go in hooks; judgment goes in reviews.

A failed grep proves little. Grep is the crudest of three recognition paths (hot index, automatic hybrid recall, deliberate search). A thing is functionally unknown only when all three miss — and the recorded-alias convention exists to make that state rare: when something acquires a second name in the wild, write it down where search can see it.
